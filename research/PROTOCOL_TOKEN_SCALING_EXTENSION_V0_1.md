# Protocol token scaling extension v0.1 (exploratory)

**Status:** post-sweep exploratory falsification; not confirmatory inference and not a model-task result.

## Question

The frozen v0.1 tokenizer sweep measured dimensions through `d=10`. It found a declining but still positive known-token premium for compact labeled fields against JSON, while the runner's fixed digit code remained expensive because both role instructions enumerate each axis/value mapping. This separate extension asks whether the compact card's repeated per-field savings eventually repay its recurring instruction premium.

The range and prediction were frozen in the separate [extension preregistration](PROTOCOL_TOKEN_SCALING_EXTENSION_PREREG_V0_1.md) after observing the original sweep. The primary sweep and its data were not changed.

## Method

- Settings: `d ∈ {20,40,80}`, `V ∈ {2,4,8,10}`, 16 deterministic episode-shaped prompt records per setting, and four candidates per receiver table.
- Three conditions: built-in compact JSON, compact labeled-fields card v0.3, and the runner's fixed per-axis digit symbols.
- Reconstructed the v0.4 sender/receiver instruction and user-content strings. Counted Qwen/Qwen3-4B tokenizer tokens at revision `eb971e9fb1f41c13b5e5a56e56886305c5ad94a0`, with no special tokens added.
- “Known total” includes both agents' input content, including the message echoed in the receiver transcript, and the ideal sender message output. It excludes receiver output, endpoint/chat-template tokens, provider caching, model behavior, and inference compute.
- The support is generated by the identity-rank modular holdout fixture. It is a deterministic cost-construction device, not a sampled benchmark or evidence about task utility.

Machine-readable measurements: [`PROTOCOL_TOKEN_SCALING_EXTENSION_V0_1.json`](data/PROTOCOL_TOKEN_SCALING_EXTENSION_V0_1.json). The file binds the tokenizer, runner, codec, card, extension-plan, and prior frozen-sweep hashes.

## Results

Mean known-content-token totals over the 16 constructed records were identical across the four tested `V` values at each fixed `d`:

| Dimensions `d` | JSON | Compact fields v0.3 | v0.3 minus JSON | Fixed symbols minus JSON |
|---:|---:|---:|---:|---:|
| 20 | 1,847 | 1,854 | +7 | +663 to +3,543 as `V` goes 2 to 10 |
| 40 | 3,387 | 3,354 | −33 | +1,303 to +7,063 as `V` goes 2 to 10 |
| 80 | 6,467 | 6,354 | −113 | +2,583 to +14,103 as `V` goes 2 to 10 |

The compact-fields/JSON known-token difference is therefore positive at `d=20` and negative at `d=40` and `d=80`, for every tested `V`. This brackets a tokenizer-and-prompt-specific cost crossover somewhere between 20 and 40 dimensions; the sweep does not locate its exact position. At `d=80`, compact fields save 113 known content tokens per constructed episode. The fixed-symbol condition remains substantially more expensive throughout the tested range, with its gap increasing as `V` grows.

The v0.3 message itself is shorter in UTF-8 than JSON by 82, 162, and 322 bytes at `d=20,40,80`, respectively. This output-only byte saving is not the reported token result: the total includes recurring instructions, both agents' request contexts, and the receiver-side message echo.

## Interpretation and limits

This is a narrow counterexample to the claim that the v0.3 card's recurring prompt premium necessarily dominates at every dimensionality. Under this exact runner construction and pinned tokenizer, enough repeated fields let its per-field savings overtake that premium. That is consistent with the setup-cost/cumulative-savings logic in [Theory §4](../docs/THEORY.md#4-a-checkable-setup-cost-crossover), but it does not establish a reusable-protocol amortization horizon: these instructions are charged on every episode and no persistent cache is assumed.

The result does **not** show that compact fields improve accuracy, carry more useful information, reduce actual endpoint billing, or outperform JSON at realistic model-task quality. These are synthetic prompts with four candidates; dimensions 40 and 80 can also approach context limits once model-generated answers, templates, or other retained history are included. The token counts are tokenizer content counts, not service-reported usage. There is one tokenizer, one card, one prompt constructor, and no model execution.

P19c is supported on the tested points (`d=40,80`) and remains exploratory because the extension range was selected after the frozen v0.1 measurements. A new preregistered confirmation should target the 20–40 interval, retain all conditions and costs, and pair the cost comparison with a gated task-success experiment. Until that exists, this is a cost-geometry finding only.

## Reproduction

With the pinned tokenizer already present locally:

```powershell
python research/audit_protocol_token_scaling.py `
  --tokenizer-json .cache/tokenizers/hfhub/models--Qwen--Qwen3-4B/snapshots/eb971e9fb1f41c13b5e5a56e56886305c5ad94a0/tokenizer.json `
  --output research/data/PROTOCOL_TOKEN_SCALING_EXTENSION_V0_1.json `
  --extension
```

This audit tokenizes strings only. It loads no model weights and makes no inference calls.
